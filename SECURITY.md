## 1. Authentication

### Password Security
- **Hashing**: bcrypt with cost factor 12
- **Salt**: Automatically generated by bcrypt
- **Minimum Length**: Enforced at application level
- **Storage**: `password_hash` column (VARCHAR 255); plaintext passwords never stored

### Login Mechanism
- Accepts either **username** or **email** plus password
- Validates credentials via `authenticate_user()` in `services/user_service.py`
- Returns JWT access token and refresh token on success
- Failed attempts return generic `Invalid credentials` message (no enumeration)

### Registration
- Validates username and email uniqueness
- Hashes password before storage
- Creates user account with `is_active=True`, `is_verified=False` (email verification future)
- Issues tokens on successful registration

### Session Management
- Access tokens: short-lived (15 minutes)
- Refresh tokens: long-lived (7 days), stored hashed in database
- Multi-device support: multiple active refresh tokens per user
- Session revocation supported individually or in bulk

## 2. Authorization

### Route Protection
- All protected routes use `get_current_user` dependency
- Dependency validates JWT, loads user, checks `is_active`
- Returns 401 if token missing/invalid/expired or user inactive

### Conversation-Level Authorization
- `is_participant(db, conversation_id, user_id)` checks `conversation_participants` table
- Enforces `left_at IS NULL` (active membership)
- Used by conversation, message, and attachment routers
- Returns 403 if user is not an active participant

### Attachment-Level Authorization
- `AttachmentService.verify_attachment_access()` checks conversation membership
- `AttachmentService.verify_ownership()` ensures only uploader can delete
- Returns 404 for non-existent attachments (prevents enumeration)
- Returns 403 for unauthorized access

## 3. JWT Lifecycle

### Token Structure
- **Algorithm**: HS256
- **Access Token Claims**:
  - `sub`: user ID
  - `type`: `"access"`
  - `exp`: expiration timestamp
  - `iat`: issued-at timestamp
- **Refresh Token Claims**:
  - `sub`: user ID
  - `type`: `"refresh"`
  - `exp`: expiration timestamp
  - `iat`: issued-at timestamp

### Expiration
- Access tokens: **15 minutes**
- Refresh tokens: **7 days**

### Storage
- Client stores tokens securely (HTTP-only cookies recommended)
- Server stores refresh token hashes in `RefreshTokens` table
- Token hashes: SHA-256 before storage

### Revocation
- Refresh tokens marked `revoked_at` on logout or admin action
- Revoked tokens rejected on refresh attempt
- Bulk revocation supported (e.g., password change)

### Validation
- `decode_token()` validates signature, expiration, and type
- `get_current_user` additionally verifies user exists and is active
- Refresh endpoint validates token type is `"refresh"` before issuing new access token

## 4. WebSocket Security

### Authentication
- WebSocket endpoint: `/ws` (single endpoint, no parameters in URL)
- Client sends `{"type": "auth", "token": "<jwt>"}` as first message
- Server validates JWT using same `decode_token()` as REST APIs
- Token travels inside encrypted WebSocket frame, never in URL

### Authorization
- After auth, client sends `{"type": "join_conversation", "conversation_id": "<uuid>"}`
- Server calls `is_participant()` before adding to subscription set
- Non-participants receive error and socket closed with code 4403

### Connection Management
- `ConnectionManager` singleton tracks `active_connections` and `conversation_subscriptions`
- Disconnect removes connection from all subscription sets
- Dead connections cleaned up on failed sends

### Protocol
- JSON message format
- Heartbeat via `ping`/`pong` messages
- Close codes: 4401 (auth failed), 4403 (forbidden), 4400 (malformed), 4405 (server error)

## 5. IDOR Prevention

### Principle
Never trust client-supplied object identifiers without server-side authorization.

### Implementation
1. **No IDs in URLs**: WebSocket endpoint is always `/ws`
2. **Database authorization on every access**: `is_participant()` queried before every subscription or message access
3. **Attachment access**: `verify_attachment_access()` checks conversation membership
4. **Consistent authorization**: Same `is_participant` function used across REST and WebSocket paths
5. **404 for missing resources**: Non-existent attachments return 404, not 403, to avoid enumeration

### Examples
- WebSocket subscription: DB lookup required
- Message retrieval: participant check enforced
- Attachment download: conversation membership verified

## 6. File Upload Security

### Allowed Types
- Phase 8.1: PNG, JPEG, WebP only
- MIME type allowlist enforced server-side

### MIME Detection
- **Magic bytes** detection via `detect_mime_type()`
- Never trusts `Content-Type` header from client
- Reads file content and matches against known signatures

### Filename Sanitization
- Strips path traversal sequences (`../`, `..\\`)
- Removes null bytes
- Removes path separators
- Blocks double extensions (e.g., `image.jpg.exe`)
- Blocks known executable extensions
- Truncates to max length (255 chars)

### Image Processing
- EXIF metadata stripped (GPS, camera info)
- Images re-encoded server-side (removes hidden data)
- Decompression bomb detection via Pillow
- Thumbnail generation server-side

### Storage
- Files stored with UUIDv4 names (never client-supplied)
- Storage outside web root
- Never expose filesystem paths to clients
- Atomic writes (temp file + `os.replace`)

## 7. Attachment Security

### Upload Pipeline
1. Rate limit check
2. Conversation membership verification
3. File size validation (max 10 MB, reject 0 bytes)
4. Filename sanitization
5. MIME detection via magic bytes
6. Extension validation (must match MIME)
7. Double extension check
8. Image processing (EXIF strip, re-encode, thumbnail, bomb detection)
9. SHA-256 checksum (server-side)
10. UUIDv4 stored filename
11. Save to disk
12. Create DB record
13. Audit log

### Access Controls
- Only conversation participants can access attachments
- Only uploader can delete their own attachment
- Soft delete preserves audit trail
- Hard delete on disk when deleted

### Headers
- `X-Content-Type-Options: nosniff` on all downloads
- `Content-Disposition: attachment` for downloads (prevents inline rendering)
- `Content-Disposition: inline` for thumbnails

## 8. Input Validation

### General Principles
- All inputs validated via Pydantic schemas
- Strict schemas reject extra fields (`extra="forbid"`)
- UUIDs validated before use
- Pagination limits enforced (1–100)
- String lengths constrained

### Specific Validations
- Username/email uniqueness checked at registration
- Passwords minimum length enforced
- Message content non-empty validation
- Message type allowlist: `text`, `image`, `file`, `audio`, `system`
- Conversation participant count validated (min 2 for groups)
- File size bounds enforced
- MIME type allowlist enforced

### SQL Injection Prevention
- SQLAlchemy ORM used exclusively
- No raw SQL queries
- Parameterized queries via ORM

### XSS Prevention
- Content stored encrypted (not rendered server-side)
- Responses serialized via Pydantic (auto-escaping)
- No server-side HTML rendering of user content

## 9. Rate Limiting

### Attachment Uploads
- **Per user**: 10 uploads per minute
- **Concurrent**: 3 simultaneous uploads per user
- **Implementation**: In-memory `RateLimiter` class with thread safety
- **Response**: HTTP 429 with `Retry-After` header

### Future Rate Limiting
- Login endpoint: 5 attempts per 15 minutes per IP
- Registration endpoint: 3 attempts per hour per IP
- Token refresh: 10 attempts per 5 minutes per user
- AI endpoints: 20 messages per hour per user

## 10. Logging Policy

### What We Log
- Authentication events (success/failure)
- Message send events
- Attachment upload success/failure
- Authorization failures (IDOR attempts)
- Rate limit violations
- MIME type mismatches
- Oversized uploads
- WebSocket connection events

### What We Never Log
- JWTs or refresh tokens
- File contents
- Absolute storage paths
- Passwords or password hashes
- Private cryptographic keys

### Log Format
- Structured logging via Python `logging` module
- Attachment logs use dedicated logger `qrc.attachments`
- Include user ID (first 8 chars), action, and relevant context
- Include IP address and user agent where available

### Audit Trail
- `AuditLog` table tracks security-relevant events
- JSONB `event_data` field for flexible metadata
- Indexed on `user_id`, `event_type`, `created_at`

## 11. Future Post-Quantum Cryptography

### Current State
- Symmetric encryption uses AES-256-GCM (quantum-resistant)
- JWT signed with HS256 (classical, but short-lived)
- No post-quantum key exchange or signatures implemented yet

### Planned Implementation
- **ML-KEM (FIPS 203)**: Key encapsulation for session key exchange
- **ML-DSA (FIPS 204)**: Digital signatures for message authentication
- Key pairs generated during user registration
- Private keys encrypted with AES-256-GCM before storage
- Key rotation support via versioning
- Backward compatibility for old messages

### Migration Path
1. Add `UserKeys` table for PQC key pairs
2. Generate keys on registration/login
3. Establish session keys via ML-KEM
4. Sign messages with ML-DSA
5. Rotate keys periodically
6. Maintain hybrid mode during transition

## 12. Known Limitations

### Classical Cryptography
- JWT uses HS256 (HMAC-SHA256), not post-quantum
- No perfect forward secrecy in current message encryption
- Session keys not rotated per-message

### File Uploads
- Image-only in Phase 8.1; broader file types future
- No virus scanning (future enhancement)
- No content-based hash deduplication

### Rate Limiting
- In-memory rate limiter; resets on server restart
- Not distributed across multiple server instances

### Testing
- Test coverage expanding; not yet comprehensive
- No load/stress testing completed
- No formal penetration testing

### AI Features
- Local LLM requires GPU for reasonable performance
- Context window limits conversation length
- No prompt injection filtering (future)
